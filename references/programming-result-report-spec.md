# 编程结果说明报告规范

仅当用户在编程前选择需要报告时读取本规范。报告描述最终程序和实际运行证据，不是编译环境版本记录，也不能替代 `compile-environment/` 中的环境 PDF。

## 格式与位置

- 优先使用用户指定的格式、名称和路径。
- 用户只回答“需要”而未指定时，默认生成 Markdown：`docs/编程结果说明_yyyyMMddHHmm.md`。
- 若项目已有报告目录或命名约定，沿用既有约定；目标文件存在时生成新的时间戳版本，不得静默覆盖。
- 在最终代码与验证结果稳定后生成。报告生成后若代码或验证证据变化，交付前同步更新报告。

## 必含内容

1. **任务概览**：用户目标、实现范围、明确非目标、报告生成时间和时区。
2. **程序详细说明**：用途、使用场景、总体架构、模块关系、主要数据流和控制流。
3. **文件与功能分块**：逐个说明关键文件、模块、类、函数和功能分块的职责及相互调用关系。
4. **自定义变量**：以表格列出名称、所在文件、类型、默认值或安全示例、单位、允许范围、作用、联动约束和修改后的影响。秘密配置只列变量名与来源，不记录值。
5. **输入、输出与接口**：输入格式、输出格式、文件、网络接口、命令参数、返回值及错误行为。
6. **关键实现与限制**：主要算法或业务规则、异常处理、边界条件、安全与性能考虑、平台假设和已知限制。
7. **运行方法**：前置条件、唯一项目环境、启动/构建/测试命令，以及必要的配置步骤；可引用对应的最新编译环境 PDF。
8. **程序运行结果**：记录实际命令、运行时间与时区、环境标识、输入或测试数据、退出码/状态、关键输出、日志摘要、指标和生成产物。
9. **验证结论**：通过、失败与跳过的检查，失败原因、未覆盖范围、剩余风险和可复现步骤。
10. **变更与后续定制**：本次新增或修改内容，以及用户最可能继续调整的变量、模块和扩展点。

## 运行结果证据规则

- 只写入本次实际观察到的结果；不得把预期行为、示例输出或计划测试写成已完成事实。
- 每项结果注明“实际执行”“未执行”“失败”或“跳过”。未执行和跳过项必须写明原因。
- 输出过长时保留关键片段并给出完整产物的项目相对路径；不得粘贴秘密、令牌、私人路径或完整敏感日志。
- 若程序无法运行，报告仍可生成，但标题或结论必须清楚标示“运行未完成”，并记录阻碍、诊断证据和用户可执行的下一步。
- 报告中的版本、命令、文件名和结果必须与交付的最终程序一致。

## 可读性检查

- 先给出结论，再展开实现与证据；标题层级清楚，表格不过宽，命令与普通说明分开。
- 术语首次出现时解释，避免只用内部简称。
- 对复杂流程可使用简短的文本流程或表格，但不要为了装饰添加无信息量内容。
- 交付前核对所有链接和项目相对路径，确认用户能据此定位代码、配置与运行产物。
